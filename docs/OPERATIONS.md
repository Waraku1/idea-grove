更新: 2026-10-05。管理機能と手順の実装済み部分と、実アカウントで行う設定を区別する。

## 権限と管理対象

| 役割 | 担当・範囲 |

| サービス所有者 | Waraku1（GitHub ID: 153403020）。Cloudflareとソースリポジトリの所有・契約・公開判断。アカウント側の権限設定は接続後 |

管理画面はリリース、DB接続設定、認証設定、保存停止の状態だけを示す。内容やシークレット、他ユーザー一覧は表示しない。Cloudflareの管理権限にはDBを技術的に読み取れる能力があるため、利用者への説明と最小権限を守る。第三者へ管理権限を勝手に渡さない。

Cloudflare / GitHubで2要素認証を設定し、復旧コードは所有者が安全に保管する。公開用OAuth App、限定API Token、SESSION_SECRETの所有と更新を管理する。パスワード、Client Secret、API Token、世界のバックアップはGit・Issue・ログ・チャットに貼らない。

## 費用・稼働確認

手動の定期確認方針。通知や有料監視サービス、定期ジョブは未作成。

- 公開前と更新前: Workers **Free**、有料購読なし、課金サービス追加なしを確認。releaseコマンドも契約を読み、確認不能なら停止する。
- 公開後の初期期間は日次、その後は週次: Cloudflare標準のWorkerリクエスト数、CPU時間・失敗率、D1 row reads/writesと保存量を確認する。アカウント全体の合算を読む。
- 日次上限の70%に近づいたら原因を確認。90%で `APP_READ_ONLY=true` にして保存を止める判断を行う。これらは手動運用の閾値であり、自動監視済みとは扱わない。
- DBが400MBを超えたら新規利用者の募集を停止し、不要データの消去とバックアップを案内。450MB以上では保存停止を検討する。利用者の内容や履歴を勝手に削除しない。
- 日次上限超過時の停止は0円運用の仕様。UTC 00:00のリセットを待つ。上限回避のためPaidへ切り替えない。保存量上限は日次リセットでは解決しない。

`/healthz` は構成確認用であり、DBへの実際の読み書き成功や課金状態を証明しない。管理画面も課金・使用量をリアルタイムで取得しない。実稼働は標準メトリクスと検証用アカウントで確認する。外部監視の連続ポーリングは日次quotaを使うので導入しない。

## 保存停止と障害対応

1. Cloudflareで `APP_READ_ONLY` を `true` に設定してデプロイする。ローカル設定も合わせ、次回releaseで戻してしまわないようにする。
2. APIの更新・復元・消去を503で止める。現在状態・履歴の閲覧、現在状態のJSON exportは、読み出しquotaとWorkerの稼働が残っていれば利用できる。内容の下書きは端末に保持する。
3. quota、DB容量、CPU超過、GitHub認証、天気取得、直近のリリースを確認する。エラーログに本文・OAuth code・token・Cookieを記録しない。
4. 原因がコードなら直前のWorker versionへ戻す。DB復旧は別手順とし、コードのロールバックだけでDBを巻き戻さない。
5. 検証用アカウントで読込・保存・再読込が成功したらFree契約を確認して停止を解除し、時刻・原因・対処・影響を記録する。

## バックアップ

利用者はSettingsで現在世界のJSONを持ち出せる。重要な作業の前後に本人が保管する。成長履歴は現行のJSON exportに含まれない。

管理者は**DB変更の前と復旧の前**にCloudflare D1 exportで現在のDBを取得する。SQLは全利用者の私的な内容を含むため、暗号化した所有者管理の保管場所に置く。ソースとは分離し、リポジトリや公開サイトに含めない。この時点で自動バックアップや安全な外部保管先が作成済みとは扱わない。日常の復旧はD1 Freeの7日Time Travelを利用し、SQLの長期保管が必要なら所有者が無料の既存保管先を明示して設定する。

## 内容消去を守る復旧

公開版の「Delete my grove and history」は、確認後に本人のworlds / world_eventsを同一トランザクションで消去し、account_erasuresに固定IDと消去時刻だけを記録する。他人の世界を消去しない。現在端末の下書き・天気設定を消し、現在セッションを終了する。他端末の保存物・ダウンロード済みファイルは本人が別途消去する。

過去のDB復旧で消去済み本文を再公開しないため、次の順序を守る。

1. アプリへのアクセスを一時的に停止する。`APP_READ_ONLY` だけでは閲覧が残るため、復旧中は準備中応答のWorker versionへ切り替える。誤って旧データが見える時間を作らない。
2. **復旧前の最新** account_erasuresを安全な場所にexportする。全DBのバックアップも取る。失われて最新の消去記録が確認できない場合は本番の過去復旧を中止する。
3. 復旧対象時点と範囲を確認し、Cloudflare Time Travelを実行する。
4. 最新の消去記録を復旧DBへ再適用する。owner_idごとに最も新しいerased_atを保持する。
5. 保存停止のまま以下のSQLで過去の消去対象を取り除く。消去後に本人が作り直した新しい世界はupdated_atによって残る。

```sql
DELETE FROM world_events
WHERE EXISTS (
  SELECT 1 FROM account_erasures e
  WHERE e.owner_id = world_events.owner_id
    AND world_events.occurred_at <= e.erased_at
);
DELETE FROM worlds
WHERE EXISTS (
  SELECT 1 FROM account_erasures e
  WHERE e.owner_id = worlds.owner_id
    AND worlds.updated_at <= e.erased_at
);
```

6. 検証用データで所有者分離、消去、復旧後のrevision、履歴再生を確認する。アプリを保存停止状態で再公開し、影響する利用者に確認後、保存を再開する。人への連絡は所有者の明示した経路と指示に従う。

全DBの巻戻しは他人の最新状態も失うため最後の選択肢。利用者1人の問題は本人のJSON復元を第一候補にする。削除SQLや本番復元をテスト目的で実行しない。

## リリースとロールバック

- 公開日時、Git SHA、Worker version ID、担当者、Free確認結果、実サイト確認結果を1件ごとに記録する。ソースは非公開リポジトリに保存する。
- `npm run release:cloudflare` を使用し、仮設定や契約のチェックを迂回しない。UI変更時は3D静止画と実ブラウザの主要操作を確認する。
- 直前の正常Worker versionをCloudflareで保持し、失敗時はそのversionへ戻す。公開URL・OAuth callbackは同じまま。互換性のないDB変更には別途バックアップと移行計画を用意する。
- SESSION_SECRETの漏洩時は新しい乱数へ置換して全利用者を再ログインさせる。GitHub Client SecretやCloudflare Tokenの漏洩も各提供元で失効・再発行し、原因を修正してから公開を再開する。
- 契約・2要素認証、非公開リポジトリ、復旧訓練はアカウント接続後に確認する。準備したコードや文書だけをもって、管理体制が実環境で稼働済みとは記録しない。
